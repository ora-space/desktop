# Agent 停止责任

[English](session-stop.md) | 中文
Agent 启动使用 `session-attempts` 下独立并刷盘的尝试锁。插件和每个由宿主启动的子进程继承锁描述符；
刷盘的 PID、启动时间和 boot 线索也防止关闭继承描述符的子进程被误判为停止。会话停止或 MCP 替换 Agent 进程时，Node 先关闭 spawn 闸门，
立即杀掉尝试标记认领的进程（见下文）和持久线索标识的原进程组。插件可能在收到 ora/shutdown 前退出。Node 等待生命周期收尾以取得诊断，
并在释放资源前核验停止证据。spawn 闸门关闭后禁用自动重启。发送信号、超时、单独取得空闲锁都不是完整停止证据。未确认的尝试在重启后仍保留包租约、
工作负载视图和 checkout 责任。终止事件和 Revision 准入等待停止确认及资源释放。

spawn 闸门启动的每个进程还带有 `ORA_SESSION_ATTEMPT=<attempt>`，后代进程会继承它。账本登记尝试之前，
`session-attempts/<attempt>.mark` 先持久记录尝试的开始时间（boot 时钟 tick）和其进程运行所用的用户，账本行也记下这个尝试
有范围记录。这样能找到离开全部原进程组、又丢掉继承锁的工具作业，例如 Agent 工具 shell（OpenCode 的 bash 工具、Claude 的
Bash）在 `setsid` 下执行的 `cmd &`：它被 init 收养，又由 Bun 这类会关闭继承描述符的运行时启动。存活进程只要带有该标记且在
尝试开始之后启动，或其父进程属于该尝试，就属于该尝试；主线程已退出但其他线程仍在运行的进程同样算存活。终止时先经 pidfd 用
SIGSTOP 冻结所有这类进程，反复扫描直到不再出现新进程（最多 32 轮），再全部杀掉，然后才向原进程组发信号。停止证明还要求连续
两次扫描都干净：仍有被认领的存活进程时尝试视为运行中；扫描失败（procfs 读不了、描述符耗尽），或 Node 以其他用户运行且没有
`CAP_SYS_PTRACE` 时出现了尝试用户的不可读进程，证据为未知。

| 账本范围记录标志 | `.mark` 范围记录 | 锁、线索与扫描都干净时的证据 |
| --- | --- | --- |
| 有（本 Node 登记的每个尝试） | 有效 | `lock_processes_and_marks` |
| 有 | 缺失、损坏或不可读 | 未知，转交对账 |
| 无（标记出现之前登记） | 不读取 | `lock_and_processes`，与以前相同 |

这两种同一 boot 的证明都不能用于 `after-host-reboot` 对账，也不能解除 `legacy_unknown`。schema 16 排在 schema 15（取消轮次的结算）
之后，在一次表重建中加入新的证明值和标志，已有行一律不带标志；旧程序拒绝打开 schema 16 的数据库。

**开销与上限。** 扫描和杀进程从不在 Node 的运行时线程上执行。每个 Node 只有一个阻塞 worker，所以它所有会话的停止观察都是串行的：
一个会话结束时其他会话还在收尾，或者 restore 轮询和确认重叠，都要排队。每次停止观察（一次终止加两次证据扫描）有 5 秒预算，
包括等待 worker 的时间。把等待算进去是有意的：正因如此，排在卡住的读取后面的观察才会以未知放弃，而不是无限排队，也不会再起
新线程。超出预算的观察，无论是在排队还是因为某次 `environ` 读取卡在挂起的 FUSE 或 NFS 上，都算作未知，并在确认期限前重试；
worker 忙只会推迟停止，不会确认停止。尝试未停下时，两次观察之间先等 25 ms，逐次加倍到 1 秒。无论进程有多少，一次扫描同时只
打开少数几个描述符，并且只读取在尝试开始之后启动的进程的环境。

**读取卡住时。** 卡住的读取会一直占着 worker，直到它返回：挂载恢复，或者它等待的进程退出。在此之前，这个 Node 所有会话的
停止观察都是未知，停止到期限后记为 `stop_unconfirmed`；不会产生假的确认。重启后的 Node 会扫描同一个窗口，可能再次遇到同一个
读取。已冻结的进程不受影响：任何进程被冻结的时间都不超过 2 秒，之后看门狗即使在扫描卡住时也会杀掉所有已冻结的进程，剩下的
扫描轮次改为直接杀而不再冻结。已冻结、尚未退出、却无法为这次杀掉而重新 pin 的进程（例如 Node 的描述符耗尽）会保持冻结，
直到下一次观察把它杀掉；在此期间扫描仍会认领它，所以它的尝试仍是运行中。关闭也有上限：服务返回之后，Node 最多再等 5 秒
仍在运行的阻塞任务（正常情况下只有这样被放弃的读取），然后退出。

**什么会被杀掉、在什么时候。** 会话结束时（EndSession、Agent 失败、导致会话结束的取消、优雅关闭、Node 崩溃后的重启恢复），
以及 MCP 生命周期替换会话的 Agent 进程时，在确认停止之前，所有带该尝试标记、或经带标记的父进程被认领的存活进程都会被杀掉。
覆盖范围是 Agent 启动且保留了环境的进程：工具后台作业、作为普通程序运行的开发服务器和文件监视进程、MCP 服务和语言服务，
以及会话中的工具启动的共享守护进程，例如 Gradle daemon 或 sccache 服务。轮次之间不会杀任何进程。需要守护进程在会话结束后
继续运行的用户，必须在 Ora 之外启动它；由 Agent 启动的守护进程即使还有其他会话或程序在用，也会随会话一起结束。并非所有守护
进程都在覆盖范围内，见下面的已知限制。

**已知限制。** 标记只在 Linux 上提供，保证等级仍是 BestEffort。
- 清空环境（`env -i`）、改写自身环境区域（例如 PostgreSQL、nginx 把进程标题写在环境区域上），或把自己设为不可 dump 的进程，
  只在父进程属于该尝试时才能找到；一旦成为孤儿（守护进程通常如此）就看不到了，会在会话结束后继续运行。
- 属于尝试用户、Node 读不到其环境的孤儿进程不计入，也不会让证据变成未知。原因是无关程序（ssh-agent、带 file capability 的
  程序）同样读不到，把它们算进去会挡住所有停止。换了用户的孤儿（经 `sudo` 或其他 setuid 程序）同样不计入。
- 由尝试之外的服务代为启动的进程（例如经 `docker run` 或 `systemd-run`）不会继承标记，不会被停止。
- Node 自己若运行在另一个尝试的标记下（外层 Agent 启动的嵌套 Node），会把两者一起传下去（`outer:attempt`），所以外层尝试停止时
  也会杀掉内层 Node 的尝试；内层 Node 只认领列出自己尝试的进程。
- 标记不是秘密：能读到它的进程可以启动带标记的进程，这些进程会随尝试一起被杀，但无法让 Node 向尝试开始之前启动的进程发信号。
  不停地启动这类进程，可以把停止拖到 `stop_unconfirmed`。
- 同一次扫描中 PID 被别的进程接手时，它不会被当作父进程；扫描的几毫秒里其他 PID 复用竞争仍可能发生，概率很低。

**部署前提。** Node 与 workload 以同一用户运行，或 Node 具备 `CAP_SYS_PTRACE`。Desktop 与 cloud v2 都以同一用户运行。否则，
例如 root Node 配置了 `process.workload_uid` 并运行在默认的 Docker 能力集中，Node 读不到任何 workload 的环境：它在启动时记录告警
并照常服务，但尝试窗口内只要有 workload 用户的存活进程（包括另一个会话的进程），这个尝试的证据就是未知，停止会以
`stop_unconfirmed` 结束，带标记的作业也找不到。这项检查在启动时校验 Agent 配置时执行，只看有效能力集（`CapEff`）：Yama 的
`ptrace_scope` 或 LSM 仍然拒绝读取时检测不到，这时证据同样是未知，但不会有告警。

`node.session_stop.confirmation_timeout_ms` 默认为 600000，必须为正数。首次期限持久化，重试不会延长。
跨 boot 证明需要显式配置且与原宿主匹配的 `trusted_host_id`，或由部署提供存储隔离保障的
`single_mount_with_storage_fencing: true`。不会把容器 machine-id 推断为可信宿主身份。schema 14
迁移前盘点旧的运行中 Agent execution，将其保留为 `legacy_unknown`。

root 可向运行中的 Node 请求核对证据：

```sh
ora-node reconcile-session-stop /absolute/node/home EXECUTION ATTEMPT REQUEST_ID maintenance recheck
```

原因可选 `maintenance`、`probe-capacity`、`legacy-upgrade`；模式可选 `recheck`、`after-host-reboot`。
私有 socket 使用内核提供的对端 UID 认证。同一请求 ID 和输入返回已存结果，冲突复用被拒绝。
一次 recheck 的观察、终止和等待总共不超过 10 秒：每一步只拿到这个上限剩下的时间。
请求、原始身份、观察和结果均有审计，但不包含命令、Settings 或凭据。确认停止不会直接报告资源已释放。
中断的审计重新获取证据。已确认且资源已释放的明细在七天后、没有 outbox 或未完成审计引用时清理，
保留汇总和审计；未确认明细不按时间自动清理。

Node home 和独立工作负载包视图必须位于支持的本地文件系统及同一设备上。启动时检查硬链接能力，
创建视图时拒绝跨设备复制。精确 MCP 版本租约允许另一已验证的 MCP 版本并存，但禁止修复或删除在用字节。
其他插件类型仍按整个 ID 互斥，改变包类型不能绕过活动或重启后保留的租约。

生命周期会话在 load 失败或断连后保留 provider session ID 和上次 active MCP revision，不通过新建
provider session 或回放 transcript 修复 MCP 失败。下一轮可对每个 generation 重试一次，不做周期性刷新重试。
MCP 包版本变化，或首次 setup 后第九次运行期 load，会仅替换本 execution 的 Agent 进程。Node 先记录停止请求，杀掉旧尝试带标记的进程和原进程组，再等待旧 supervisor 退出。旧 supervisor 完成清理后才安装后继进程。替换前准备最新目标，
确认旧进程停止后才注册新尝试；HOME、checkout、model grant 和 ora-git 上下文继续属于原 execution。
等待清理时的新目标合并到最新代际。

宿主健康独立于 ACP 收敛。解析成功后排队一次自动探测；手动 attempt 按成员合并。Node 在会话间轮转调度，
全局最多 8 个、每会话最多 2 个名额，包含保留和重启恢复的清理责任。取得名额后开始十秒预算：握手最多八秒，
其余时间用于清理。stdio 使用会话的精确包视图、checkout、工作负载身份，仅注入显式设置及 PATH、LANG、LC_ALL、TMPDIR 等无授权的运行必需环境；HTTP 使用 Node 身份，
禁用代理与重定向。握手和清理都成功才报告 Healthy。旧代结果不能更新当前健康；未知清理继续保留名额、租约和
持久停止责任。不通过自动失败重试或 TTL 把健康观察变为准入依据。

探测清理超过十秒时只发布一次 `mcp_probe_timeout`，独立的原停止确认期限仍然有效，到期才标记
`stop_unconfirmed`。随后停止自动等待，保留名额和租约；root 显式对账记录停止证明后唤醒资源 owner。
root 可以向 `session-stop.sock` 发送以换行结尾的 `{"operation":"probe_capacity"}`，查询总名额、
执行中数量、cleanup_pending、排队意图及可用名额。会话查询只暴露匿名容量状态及自己的成员。

升级部署要求：Node home 和包/工作负载视图必须位于支持的本地文件系统。新增停止证据检查会拒绝
NFS、9p、virtiofs 上的 home；升级前先排空会话，再将部署拥有的数据迁移到受支持的本地文件系统。
把未确认责任复制到另一台主机不构成停止证明。

正常结束、自动恢复和 root 对账在持久确认后都会唤醒探测 owner。root 的 probe_capacity 还返回具名残留：execution、attempt、state 和原始 bound_at_ms，可直接用于停止对账；会话查询仍只暴露匿名容量。

探测 owner task panic 会使整个 Node 失败退出，保留槽位、精确版本租约和持久责任，由重启恢复证明清理完成；不支持丢失 owner 后继续服务。stop 请求和 kill_all 的结果仅用于诊断，停止证明来自原锁、进程线索和尝试标记扫描，或配置允许的可信重启证据。

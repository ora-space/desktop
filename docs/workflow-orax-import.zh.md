# 工作流 orax 导入

[English](workflow-orax-import.md) | 中文

`kind = "workflow"` 的插件包是工作流文档的投递载体。导入一个这样的包会**既安装插件、又把包内每份文档变成一个工作流并发布一个快照**，用户可以一步拿到一组可运行的工作流，而不必逐个导出再导入。

导入的工作流是**用户数据**，寿命长于承载它们的包：卸载插件不会删除它们。

## 包布局

```
my-workflows/
├── orax.toml            # kind = "workflow"；无任何 kind 专属 section
├── assets/workflows/
│   ├── 1.0.0.json
│   └── release.reactflow.json
└── logo.svg             # 可选
```

- `assets/workflows/` 必需，至少一份 `*.json` 文档，至多 256 份。
- 只有**直接**位于该目录下的普通 `*.json` 文件才算工作流。README、子目录、符号链接一律**忽略**而非拒绝——约定是「此目录下每份文档都被导入」，一个多余文件不构成拒绝整包的理由。
- 包是**无进程**的：不含 `main.js`，宿主不为它启动 Deno 运行时，`orax.toml` 也不带 kind 专属 section。`[workbench]` 与 `[webview]` 在该 kind 上被拒绝，与其他未定义这些段的 kind 一致。

清单层面的规则沿用[插件打包格式](../specs/plugin-packaging.zh.md)对所有 kind 的规定，本文只覆盖 `workflow` 新增的部分。

## 文档格式

工作流文档就是编辑器导出的工作流文件，**原样存储**。从工作流库导出一个工作流，把文件丢进 `assets/workflows/` 即可，中间不需要任何改写。

```json
{
  "id": "d90c3588-1238-444d-afb4-908091277789",
  "name": "发布流程",
  "version": "1.0.0",
  "viewport": { "x": 0, "y": 0, "zoom": 1 },
  "nodes": [
    {
      "id": "start",
      "type": "workflow",
      "position": { "x": 120, "y": 260 },
      "data": { "kind": "start" }
    }
  ],
  "edges": [],
  "annotations": [],
  "globalVariables": []
}
```

- `name` 必需，成为工作流名。工作流名必须唯一，因此名字与既有工作流冲突的文档会被**拒绝**，而不是静默改名。
- `version` 可选，见下节。
- 其余内容——包括编辑器的 React Flow 运行时字段（`measured`、`selected`、`dragging`、`zIndex`）以及导出文件自身的 `id` 与 `updatedAt`——都作为快照 `graph` 的一部分原样存入，不做解释。`graph` 列对定义层是不透明字符串，运行引擎只读 `nodes` 与 `edges`，编辑器在首次保存时自然丢掉运行时字段。**保持文档完整**正是导出文件能原样round-trip的原因。

## 导入链路

导入走的是与其他本地 `.orax` 包**同一个操作**（`client.plugin.import`），没有独立的工作流导入入口。包的行为由它的 `kind` 决定，而不是由哪个按钮打开文件选择器决定。

1. 校验、解压、提交到保留的 `local` namespace。装包失败则**不会**创建任何工作流。
2. 每份文档**各自独立**地被读取与导入。
3. 单份文档：解析 JSON → 取 `name` 与可选 `version` → 经运行引擎的解析器校验图 → 创建工作流 → 发布并激活快照。
4. 响应按文档逐个报告结果：

```json
{
  "pluginId": "local/my-workflows",
  "outcome": { "state": "installed" },
  "workflows": [
    {
      "state": "imported",
      "sourceFile": "assets/workflows/1.0.0.json",
      "workflowId": "…",
      "name": "发布流程",
      "version": "1.0.0"
    },
    {
      "state": "failed",
      "sourceFile": "assets/workflows/2.0.0.json",
      "reason": "document is not valid JSON: …"
    }
  ]
}
```

图校验**复用运行引擎的解析器**，而不是另写一套，因此导入的工作流与运行时受完全相同的规则约束。永远无法执行的图在导入时就被拒绝，而不是存进去、等运行时才暴露。

## 版本推导

发布版本按以下顺序选取：

| 顺序 | 来源                                    | 示例                           |
| ---- | --------------------------------------- | ------------------------------ |
| 1    | 文档自身的 `version` 字段               | `"version": "1.0.0"` → `1.0.0` |
| 2    | 文件名去掉 `.reactflow.json` 或 `.json` | `1.0.0.json` → `1.0.0`         |
| 3    | 工作流标题                              | `发布流程`                     |
| 4    | 自动生成 `v{timestamp_millis}`          | 以上都不可用时                 |

候选值为空、超过 128 字节、为 `.` 或 `..`、为 `draft`、或含路径分隔符与控制字符时，**拒绝而非净化**——净化会导致以作者从未写过的名字发布。拒绝之后继续往下一来源回退，因此不可用的文档依然能拿到合法的自动版本。

文件名只是**回退**路径，所以只要文档自己声明了版本，重命名打包文件不会改变版本——打包工具同时写入两者正是为此。

## 失败语义

- **坏文档只连累自己。** 每份文档独立导入，一个畸形或不可执行的文件绝不阻碍它旁边可用工作流的落地。
- **坏包只连累自己。** 归档装不上时，不读取任何文档、不创建任何工作流。
- **不存在半成品。** 每份文档要么变成一个带已发布快照的工作流，要么完全不成为工作流。

## 边界（非目标）

- **裸 `.json` 工作流文件不经此导入。** 工作流编辑器有它自己的导入路径，用于用户直接选中的导出文件。这里只负责归档。
- **只导入，不导出。** 没有任何路径把工作流文档写回包内。
- **暂无 marketplace 章节。** 该 kind 目前服务本地 `.orax` 导入；为它提供 registry 列表是另一件事。

# Managed MCP ownership requires a ledger and sidecar

The independent sidecar and user-file merge protocol are superseded for the first release by ADR-0015. P1 manages one wholly Ora-owned create-only JSONC file and colocates the second ownership proof in that file's header.

Ora may update or remove an Agent-native MCP entry only when both the Agent Target's Managed MCP ledger and a matching Workspace sidecar prove ownership. This deliberately reuses the Skill Effect ownership design: the database ledger is one half of the proof, while a marker colocated with the materialized target is the other half. A Skill has one `.ora-managed.json` inside each managed directory; an Agent MCP target instead has one sidecar mapping the multiple Ora-managed entries in its shared native configuration to their managed identities. The Agent-native entry uses the readable, version-independent MCP Plugin name as its key; a user-owned entry with that key is a conflict, not an invitation to take ownership. Missing, corrupt, pre-owned, identity-mismatched, or unknown-schema sidecars and externally modified managed entries fail closed as ownership or drift conflicts. Ora neither reconstructs ownership nor overwrites drift automatically. Unknown sidecar versions are never treated as forward compatible or downgraded; a future migration must explicitly verify ledger identity and fingerprint. The first release reports exact paths and manual remediation without adding a repair UI.

Each Agent v2 adapter declares its sidecar path; OpenCode uses `.opencode/.ora-managed-mcps.json`. The adapter's Plan returns the concrete config and sidecar artifacts, after which the Host validates Workspace containment, tracked state, and local exclude policy before authorizing Apply; the Agent plugin receives no general Git-management responsibility. In a Git Workspace, Ora resolves the repository-local exclude path through Git rather than assuming a `.git` layout and must add every sidecar and any Ora-created configuration before publishing them. It does not add a pre-existing untracked user config to excludes or otherwise change that file's intended Git policy. Failure to update a required exclude blocks materialization, while non-Git Workspaces do not require this step.

In the first release, the adapter manages only an untracked Agent configuration: it edits the sole existing `opencode.json` or `opencode.jsonc`, creates `opencode.json` when neither exists, and fails when both files exist, parsing fails, either target file is tracked, or ownership proof mismatches. JSON is strict; JSONC uses localized syntax-tree edits that preserve comments, indentation, line endings, ordering, and unrelated fields. Duplicate root keys, duplicate `mcp` keys, or duplicate target MCP keys are ambiguous and fail rather than being normalized. Plan returns the whole-config observed fingerprint or equivalent CAS token; Apply rejects any intervening edit as `ObservedChanged` instead of replanning inside an immutable Prepared operation. Whole-config fingerprints stay operation-local for CAS and recovery, while each managed entry has its own persisted ledger/sidecar fingerprint so edits to unrelated Preserved configuration require replanning without becoming false managed drift.

Only local filesystem Workspaces participate in first-release materialization. A remote Workspace reports `McpMaterializationUnsupported` for its own Agent Target without blocking local targets. The Host uses shared `ora-utils::path` validation and refuses symlinks, junctions, reparse points, unsafe ancestors, and any config or sidecar artifact that can escape the authoritative Workspace; it never treats canonicalization alone as permission to follow an external target.

# Persist complete MCP generations and apply them atomically

The combined Skill/MCP generation and composite Agent Target operation are superseded for the first release by ADR-0015. P1 keeps typed Skill and MCP desired sets independent and uses the existing Workspace generation only as a coarse wake-up epoch.

The existing Workspace Effect snapshot is extended to contain both Skills and the globally Ready, exact-versioned MCP set under one generation and one worker. The worker remains the only materialization path; Session admission merely waits for this combined generation and never writes configuration. An MCP snapshot records its exact package version, definition digest, and expected current plugin-configuration revision, but never copies sensitive String values into Effect state. The first release keeps the existing overwrite-only `store.json`: reconciliation resolves values only when its revision exactly matches the snapshot, and supersedes a stale generation with the latest one instead of retaining old API Keys for historical replay.

Each Agent Target prepares a composite plan represented by the existing per-surface operations sharing one coordination batch identity. Skill directories, Agent-native config, sidecar, staging paths, and ledger transitions remain independently journaled. Atomicity is a readiness and durable-commit guarantee, not an impossible multi-file atomic rename: a crash may leave a proven subset Applied, recovery moves it forward or reports conflict, and Ora does not attempt a broad compensating rollback. Only after every artifact and ledger transition is applied and the shared Agent activation succeeds does the derived Target advance Ready. Incremental MCP-set semantics remain forbidden even though recovery tracks individual artifacts.

Writing `store.json` and enqueuing Effect propagation cannot share one transaction. Ora atomically writes the values first and then persists a coalescing propagation request; application startup and every centralized readiness-gate path compare configuration revisions and repair any request missed by a crash in between. Materialization advances `applied_generation`, while a successful shared Agent restart and Session restoration separately advance `ready_generation`. If activation fails after files were safely applied, Ora keeps those files and the applied generation, marks the target Degraded, and retries activation instead of attempting a compensating rollback. In a shared restart batch, successfully applied Targets advance after the restart while failed Targets retain their earlier ready generation and continue blocking their own admissions.

Durable operation payloads contain only Plugin IDs, exact package and configuration revisions, definition/request digests, environment variable names, artifact locators, and previous/planned fingerprints. They never serialize environment values or a complete plaintext-bearing `ResolvedMcp`. Recovery re-resolves only the exact expected `store.json` revision; a changed revision is a newer generation to process after the immutable operation completes or recovers, not permission to substitute new values into the old plan.

# 工作流包

[English](workflow-packages.md) | 中文

`kind = "workflow"` 的插件包用来交付工作流文档。导入一个这样的包会安装插件，并把它携带的每份文档变成一个带有一个发布快照的工作流，用户一步就能拿到一组可运行的工作流。导入的工作流是用户数据：卸载插件从不删除它们。决策是[工作流包格式](https://github.com/ora-space/specs/blob/main/decisions/desktop/plugin/category/workflow/0-workflow-package-format.md) ADR。

## 包结构

```text
my-workflows/
├── orax.toml            kind = "workflow"；没有种类专属的小节
├── assets/workflows/
│   ├── 1.0.0.json
│   └── release.reactflow.json
└── logo.svg             可选
```

- `assets/workflows/` 是必需的，包含 1 到 256 份 `*.json` 文档。只有直接位于该目录下的普通 `.json` 文件才算；README、子目录或符号链接会被忽略而不是拒绝。
- 包没有进程：没有 `main.js`，不启动 Deno，没有种类专属的 manifest 小节；`[workbench]` 和 `[webview]` 像在其他不定义它们的种类上一样被拒绝。

## 文档格式

文档就是编辑器导出的工作流文件，原样存储：从工作流库导出一个工作流，把文件放进 `assets/workflows/` 即可。

```json
{
  "id": "d90c3588-1238-444d-afb4-908091277789",
  "name": "发布流程",
  "version": "1.0.0",
  "viewport": { "x": 0, "y": 0, "zoom": 1 },
  "nodes": [
    {
      "id": "start",
      "type": "workflow",
      "position": { "x": 120, "y": 260 },
      "data": { "kind": "start" }
    }
  ],
  "edges": [],
  "annotations": [],
  "globalVariables": []
}
```

- `name` 是必需的，成为工作流名称。名称必须唯一，所以名称已存在的文档会被拒绝，而不是加后缀。
- `version` 是可选的（见下文）。
- 其他所有内容，包括 React Flow 的运行时字段以及导出时的 `id` 和 `updatedAt`，都原样存入快照的 `graph`，不做解释；编辑器在第一次保存时去掉运行时字段。正因如此，导出的文件可以原封不动地往返。
- 导入不筛查节点种类。编辑器加载工作流时会丢弃它无法渲染的种类（见[工作流](../workflows/workflows.zh.md#图存储)），所以要按目标 Ora 版本的节点目录来写文档。

## 导入

工作流包通过普通的本地归档导入（`importPlugin`）以及 marketplace 安装和升级导入，由包的 `kind` 决定发生什么。

1. 归档被校验、解压并提交到 `local` 命名空间。安装失败的包不创建任何工作流。
2. 然后逐份读取并独立导入文档：解析 JSON，取 `name` 和可选的 `version`，用运行引擎的解析器校验图，创建工作流，发布一个快照并激活它。
3. 响应为每份文档报告一个结果（`imported`，带工作流 id、名称和版本；或 `failed`，带原因）。

因为校验复用运行引擎的解析器，导入的工作流遵循与运行完全相同的规则；永远无法执行的文档在导入时就被拒绝。一份坏文档只影响它自己，每份文档要么变成一个带一个发布快照的工作流，要么完全不变成工作流。

### marketplace 安装与升级

通过 marketplace 安装工作流包会导入包内文档，装完即可使用；Pack 只对本次实际新装的工作流成员开启新周期并导入文档（安装前已在装而被跳过的成员不受影响）。导入出的副本是用户数据，marketplace 为每条来源路径（`(来源命名空间, 插件标识, 包内文档路径)`）保留持久记录，并按当前记录、关联副本存活状态与操作类型（安装、升级、卡片重试）判定导入，规则见[市场工作流冲突与重装恢复 ADR](https://github.com/ora-space/specs/blob/main/decisions/desktop/plugin/category/workflow/20261124-marketplace-workflow-conflict-recovery.md)：

- **存活副本保持不动**：`imported` 记录关联的副本仍然存活（`is_deleted = 0`）时，无论用户是否编辑或改名、也无论插件是否升级或卸载重装，后续安装、升级和重试都返回 `skipped_processed` 并保留该副本。
- **同名冲突可持续重试**：工作流名称按 SQLite `COLLATE NOCASE`（ASCII 大小写不敏感）查重。遇到同名时保留用户的现有工作流，来源路径写入或保留 `conflict_skipped`，并返回 `skipped_conflict`（带挡住导入的现有工作流名称以及是否为先前已知的冲突 `knownConflict`）。之后的每次安装、升级和卡片重试都会重新检查工作流库；只要把同名工作流改名或删除，再重试、升级或重装即可导入。
- **按安装周期判定已删除副本**：成功的市场安装（含卸载后重装）开启新的安装周期；对 Pack 仅限本次实际安装的成员。重装时若 `imported` 记录关联的副本已软删除，会按未交付路径重新尝试：成功则恢复该副本而不重复创建仍存活的副本；遇同名则登记本周期的 `conflict_skipped`；遇非同名失败则以读到的前状态为条件删除该 `imported` 记录回到「无记录」，使本周期内的卡片重试和升级可直接恢复（仅当条件删除本身失败时才退回「修复后卸载重装」兜底）。升级和卡片重试留在当前周期内，继续尊重已删除的选择，返回 `skipped_deleted_copy` 并提示「副本已删除，卸载后重装可恢复」。
- **卡片重试**：已安装的工作流插件卡片提供「重试导入未导入的文档」（Pack 的工作流成员在各自成员的已安装卡片上重试）。它会重新判定无记录路径和 `conflict_skipped` 路径，同时保持存活副本不动、并尊重本周期内已删除的副本。
- **条件原子提交与结果呈现**：来源状态转换以读到的前状态为条件，新副本、草稿、首个发布快照和 `imported` 记录在同一事务内原子提交；提交阶段发现并发同名时回滚并按 `skipped_conflict` 报告，不落成 `failed`。安装（包括 Pack，会标出成员标识并指向该成员的已安装卡片）和卡片重试只要遇到冲突就打开导入结果弹窗；升级仅在出现首次冲突时打开弹窗（同批已知冲突标为「仍未解决」），已知冲突和在装期间已删除副本在升级里仅以中性计数呈现——即使升级弹窗因其他文档打开，「未导入」分组也不列出已删除副本。当没有任何文档成功导入且存在失败、首次冲突或安装/重试冲突时，提示不用完整成功样式。「未导入」条目不参与 MCP / Skill 依赖判定。

本地 `.orax` 导入行为不变：仍然导入包内全部文档，同名冲突仍按该文档的失败报告。

### 卸载工作流插件

卸载确认会列出从该市场插件导入且仍然存在的工作流。卸载 Pack 时，清单只列出将被移除的成员所导入的副本。
工作流库与创建运行菜单会在副本上显示「来源插件已卸载」，用户仍可编辑副本和发起运行。运行所需的 MCP 和 Skill 仍须可用，卸载 Pack 时可能一并移除这些依赖。重装同一插件 ID 后标记消失。
本地 `.orax` 导入的工作流也会保留。由于没有市场来源记录，这些副本不出现在保留清单里，也不显示来源标记。

### 插件依赖

文档记录了它的 Agent 节点绑定了哪些 MCP 插件和 Skill，所以导入一个包可能留下引用本机尚未安装的插件的工作流。导入因此把插件依赖和逐文档结果一起报出来：带工作流文档的包导入后，插件管理页会打开导入结果，逐份读回新建工作流的图，列出它引用的每个 MCP 和 Skill 及其状态（`installed`、`unavailable`、`missing`）、使用它的 Agent 节点，以及与编辑器导入预览相同的「去安装 / 去配置 / 去查看」入口。被拒绝的文档按包内路径和后台给出的原因一并列出。

这项检查只负责呈现：它从不阻止导入，也不会自行安装任何东西；缺依赖只会在运行到使用它的节点时失败。两条导入入口用同一套规则判定依赖，所以同一个包无论从插件管理页导入还是从编辑器「导入工作流」导入，报告的依赖状态一致。

读不回图的工作流会标为无法读取，不会被当成没有依赖；有这类工作流时，结果不会给出整包的「已就绪 / 无引用」结论，只报已经读到的那部分。依赖读取中或读取失败时，导入数量、工作流名称和被拒绝文档仍然显示；目录读取失败只影响依赖判定。全部文档都被拒绝时，只列出拒绝结果，不查询依赖目录。无效 MCP 的「去查看」会把管理器搜索切到该插件 id，避免旧搜索条件隐藏目标插件及其诊断。

## 版本

发布的版本取下列来源中第一个可用的：文档的 `version`、去掉 `.reactflow.json` 或 `.json` 后的文件名、工作流标题，最后是自动的 `v{timestamp_millis}`。候选值为空、超过 128 字节、是 `.`、`..`、`draft`，或包含路径分隔符或控制字符时会被跳过，而不是清洗。所以对声明了版本的文档，改文件名不会改变版本。

裸的 `.json` 工作流文件由工作流编辑器自己的导入功能导入，不走这里；也没有任何东西会把工作流写回包里。
